## 1. 背景与目标

### 1.1 背景

项目已有 `quota`、`userRole=vip`、管理端人工改额度，缺少自助充值与订单/收款闭环。

### 1.2 产品目标

| 目标 | 说明 |
|------|------|
| 普通用户自助充值 | 购买次数包 / VIP，支付成功后自动到账 |
| 管理员收款可见 | 全站订单与收款记录可查、可筛 |
| 与创作衔接 | 额度不足时引导充值 |

### 1.3 非目标（本期不做）

- 发票、对公转账、代理分销  
- 复杂多级会员（仅 VIP 一档）  
- 强制 JWT  
- 鉴权改造（见独立鉴权文档）

## 2. 用户与场景

### 2.1 角色

| 角色 | 充值 | 收款记录 | 说明 |
|------|------|----------|------|
| 普通用户 | ✅ 自己的充值页 | ❌ 仅自己的订单 | 额度不足引导充值 |
| VIP | ✅ 同普通用户 | ❌ 仅自己的订单 | VIP 权益按现有规则 |
| 管理员 | ✅ 可走同一充值流程 | ✅ 全站收款记录 | 人工改额度作补发保留 |

### 2.2 核心场景

**场景 A：额度用尽后充值**

1. 创作页剩余次数为 0，或创建失败提示额度不足  
2. 进入充值页选套餐并支付  
3. 到账后继续创作  

**场景 B：主动加购 / 开 VIP**

从导航或个人中心进入充值页完成支付。

**场景 C：管理员查看收款**

收款记录页按时间、状态、用户筛选，查看金额与渠道。

## 3. 功能需求

### 3.1 商品

| 类型 | 示例 | 到账 |
|------|------|------|
| 次数包 | 10 / 50 次 | `quota += N` |
| VIP | 月卡 / 年卡 | `userRole = vip`，记录开通/到期 |

首期种子数据即可；后台改价二期。

### 3.2 普通用户充值页 `/user/recharge`

**入口**：导航「充值」；个人中心 / 创作页「去充值」。

**要素**：当前额度与角色、套餐列表、下单支付（PC 扫码优先；开发可用 mock）、支付结果、「我的订单」。

**规则**：未登录先登录；到账以服务端订单为准；禁止只信前端「已支付」。

### 3.3 管理员收款记录 `/admin/payments`

| 能力 | 说明 |
|------|------|
| 列表 | 全站订单分页 |
| 筛选 | 状态、时间、用户账号 |
| 列 | 订单号、用户、商品、金额、渠道、状态、支付/创建时间 |
| 汇总 | 可选：今日/本月收款 |
| 退款 | 二期 |

### 3.4 与创作衔接

- 扣次逻辑保持现有设计  
- 额度不足：明确错误码 + 前端引导 `/user/recharge`  
- 管理端人工改额度保留为客服补发

## 4. 信息架构

| 路由 | 权限 | 页面 |
|------|------|------|
| `/user/recharge` | 登录 | 充值 |
| `/admin/payments` | 管理员 | 收款记录 |

导航：登录用户见「充值」；管理员另见「收款记录」。

---

## 5. 订单状态

| 状态 | 含义 | 文案 |
|------|------|------|
| `PENDING` | 待支付 | 待支付 |
| `PAID` | 已支付且已发货 | 已支付 |
| `CLOSED` | 关闭 | 已关闭 |
| `REFUNDED` | 退款 | 已退款 |

`PAID` 与发货绑定，且必须幂等。

---

## 6. 验收标准

- [ ] 充值页可见套餐与当前额度  
- [ ] 支付（或 mock）后额度/VIP 正确，刷新一致  
- [ ] 重复回调不重复加额度  
- [ ] 用户不能查看他人订单  
- [ ] 管理员收款记录与筛选可用  
- [ ] 额度不足创作有引导

## 7. 里程碑（支付部分）

| 阶段 | 内容 |
|------|------|
| M1 | 商品/订单 + mock 发货 |
| M2 | 用户充值页 + 管理收款记录 |
| M3 | 真实微信/支付宝 |
| M4 | 退款、汇总报表 |

鉴权完成后开始 M1。

---

## 8. 风险

| 风险 | 应对 |
|------|------|
| 渠道与回调域名 | 先 mock；生产 HTTPS |
| 发货不一致 | 查单 + 幂等；人工补发 |
| 额度展示滞后 | 支付成功后刷新登录用户 |
